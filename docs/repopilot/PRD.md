# RepoPilot MVP 产品定义

## 用户与问题

目标用户是能写代码、希望基于 AI 开源项目完成个人作品或实用工具，但缺少选题依据的开发者与学生。核心任务是判断“谁遇到问题、证据在哪、已有能力是否覆盖、哪些 AI 技术适合、我能否在有限周期做出验证原型”。

需求洞察是产品假设，尚无访谈或市场规模实测。GitHub issue 代表某个用户曾报告问题，不代表普遍需求；closed 也不代表功能已实现。

## 差异与范围

相较 GitHub 搜索或 README 摘要，RepoPilot 将用户反馈、相关技术来源和个人约束放在同一份可追溯报告中。与代码 Agent 区别是本产品只研究，不下载执行目标项目、不写代码、不向 GitHub 写入。

P0：研究输入；公开 GitHub 采集；单 Agent 多节点与有界补查；三个方向或有说明的不足三个；异步历史/失败/重试/删除；用户数据隔离；手动确认收藏；反馈与采纳；Markdown 导出；Mock 测试。P1、付费、移动端、向量库、多 Agent、自动 PR 均未实现。

## 核心流程与验收

1. 登录 Karakeep，进入 RepoPilot，输入仓库、技能、1/2/4 周和目标。
2. HTTP 只创建持久化任务；后台 worker 运行图。刷新后能继续查看状态。
3. 查看实际节点轨迹、采样范围、痛点、相关技术、机会、分项评分、置信度、风险与假设。
4. 点击来源复核；确认后收藏原仓库，标记采纳/评价，复制或下载 Markdown。
5. 任务失败/部分完成可新建重试；只有本人可以查看、删除、反馈或收藏关联。

正常演示形成三个不同目标流程：人工介入恢复检查、并行工具诊断、应用依赖健康检查。均是固定 Mock 推断，来源来自录制 issue；没有实测用户效果。

## 可信度规则

报告明确区分来源事实、模型推断和待验证假设。引用从服务端 evidence store 重建；未知 ID 去掉，置信度下调。无 issue 不得断言无痛点。技术来源不足时不说“趋势”；近期能力须有日期。100 分评分仅为排序启发式，各子项有上限，总分程序求和。

## 指标定义与当前结果

| 指标 | 计划定义 | 当前证据 |
| --- | --- | --- |
| 任务成功率 | completed + partial / 全部终态任务 | 已有本地事件；没有代表性批量结果 |
| 引用有效率 | 可打开且支持论点的来源 / 人工抽样来源 | 真实 GitHub 3 条列表/详情一致；未测语义有效率 |
| 方向采纳率 | 采纳方向的用户 / 查看报告的用户 | 仅自动化自测，不能作为用户采纳率 |
| 任务时间 | startedAt 到 completedAt | 已记录实际毫秒；不宣称固定 SLA |
| 成本 | Provider 完整 usage × 已核实价格 | usage 可用时记录；价格未配置，费用为空 |

计划下一轮访谈 3–5 位目标开发者，检查建议相关性与可实现性；该人数是计划，不是现有成绩。P1 仅在真实 Provider 与核心验收全部完成后考虑。
